关键判断：**`my` 不是内置主题**，而是用户主题（`themes/` 目录下只有 5 个内置主题）。
它依赖同目录的 `github/open-sans-v17-latin-ext_latin-*.woff2` 四个字体文件。

`frame.js` 一个文件里同时包含 Markdown 解析器、导出 HTML 生成（`exportToHTML`）、
PDF 导出（`exportPDF`）与 PDF 后处理，因此它是唯一需要静态逆向的目标。

## 证据位置

- 安装目录与版本：`D:\Typora\resources\package.json`、注册表 `HKLM\...\Typora` 的 `InstallLocation`
- 版本串与 Chromium 版本：`D:\Typora\resources\conf.default.json` 相邻的 `package.json`，
  以及 `reverse-typora-export\evidence\main-process-forensics.md` 中记录的 `process.versions`
- 主题文件清单：`D:\Typora\resources\style\themes\` 与 `C:\Users\14578\AppData\Roaming\Typora\themes\`
- 本会话复制的可复用 CSS：`vendor\style\base.css`、`vendor\style\codemirror.css`、
  `vendor\themes\my.css`、`vendor\themes\github\*.woff2`

## 决策

1. 逆向对象锁定 `appsrc\window\frame.js`（渲染进程 bundle），而不是 app.asar / lib.asar。
2. 主题 CSS **直接复用磁盘上的 `my.css` 原文**，不做任何裁剪或重写；工具只需要产出
   与 Typora 完全相同的 DOM，让这份 CSS 原样生效。
3. 随 CSS 一起 vendor 四个 Open Sans woff2（否则 headless 环境下 `@font-face`
   的 `./github/...woff2` 会 404，中文/拉丁字形回退，像素必然错）。
4. 用户 `conf.user.json`（1,199 B）与 `conf.default.json`（1,199 B）都是出厂内容，
   **没有**导出相关覆盖项；导出设置（页脚 `No. ${pageNo} / ${totalPages}`、作者 `一苇`）
   只存在于运行时存储中，因此金标准 PDF 的页脚/作者只能按 `report/02` 记录的 IPC 参数复原。

## 未解决风险

- 若升级 Typora，`frame.js` 的偏移全部失效；但本文档记录的是**行为**（DOM 形状、打印参数），
  这些在 1.x 内基本稳定。
- `my.css` 的 `@font-face` 把 Open Sans 声明成 `'JetBrains Mono'`（见 `report/03`），
  这是主题作者的写法而非 Typora 机制；本工具照抄，所以视觉与 Typora 完全一致，
  但「字体名」与「实际字形」不一致这一点需要在文档里说明。
