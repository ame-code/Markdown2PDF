# 00 · 总览

## 结论

Typora 1.9.5 的「Markdown → PDF」不使用 pandoc，而是：

1. 把编辑器文档树**重新序列化**成一份**打印专用 HTML**（不是编辑器当前 DOM）；
2. 在这份 HTML 里注入 Typora 自己的 `base.css`、`codemirror.css` 与主题 CSS，
   再追加一段按需生成的打印 CSS（MathJax 样式表、标题 `::after` 占位规则等）；
3. 交给 Chromium 打印（Electron `webContents.printToPDF`，实际等价于 CDP `Page.printToPDF`），
   参数为 `{printBackground:false, marginsType:0, pageSize:"A4"}`；
4. 用内置 PDF 库（TPDFDocument 一族）做后处理：扫描 `af://` 链接注释算出每个标题的页码与
   纵坐标，写入**书签大纲**、**元数据**，再把「页眉/页脚」作为独立小 PDF 页面贴到每页顶部/底部。

本会话把这四步全部复刻成了独立工具（`bin/md2pdf.js`），并用 Typora 亲手导出的 PDF 做逐层验收：

| 验收层 | 结果 |
| --- | --- |
| 页数 / 页面尺寸 | 1 / 595.92×842.88 pt，一致 |
| 链接注释（含不可见锚点） | 3 条，URI 与矩形逐位一致 |
| 书签大纲 | `[[1,'',null],[2,'Heading 1',1],[3,'Heading 2',1]]`，一致 |
| 元数据 | Author/Creator/Producer 一致，日期格式一致 |
| 逐像素差异 | **正文 0.0000%、整页 0.0000%**（150 dpi 分带比对） |

多页 / 多级标题 / 页眉页脚的验证文档（`test/large.md`）同样正确：2 页、8 个标题、
三级嵌套书签、页码正确（见 `report/06`）。

## 未解决风险（汇总）

1. `frame.js` 里有一个「按 `File.option.preLinebreakOnExport` 决定是否注入空白折叠规则」的分支，
   默认值 `false`（即应当注入），但**实际录到的导出 HTML 里没有这条规则**。本工具按
   「跟随实际产物不注入」实现，像素验收 0.0000% 支持这一选择；若某天 Typora 的实机行为改变，
   换行与空格的处理会随之不同。
2. `cid` 编号规则无法从 Markdown 反推（Typora 计数器把行内节点也算进去）。本工具采用
   「每块 2 个 cid」的确定性分配，能复现 `af://n0`、`af://n2` 等锚点名；若文档结构变化，
   锚点名可能与 Typora 不同，但不影响 PDF 外观与书签（位置来自注释矩形，不来自编号）。
3. 图片 URL 的 `?lastModify=` 是导出瞬间的时间戳，本工具用文件 mtime，值不同、不影响像素。
4. `[TOC]` 的条目结构是按 Typora 自带 `.md-toc*` CSS 重建的（实机导出无样本），
   页码是本工具的增量扩展；页码迭代在极端文档上可能 4 遍不收敛（见 `report/07`）。
5. 定义列表（`term\n: def`）Typora 本身不支持，本工具也不支持。
6. `:smile:` 这类 emoji 短码未转换为字符（`parity` 中作为已知缺口白名单）。
7. 分发的样式表是「实测命中的声明集合」（`vendor/style/doc.css`、`code.css`），
   选择器名属于与 Typora 一致的 DOM 契约，因此仍是一份派生数据；换主题或新增构造
   必须重跑 `npm run css:audit && npm run css:build` 并重做像素验收（见 `report/09`）。
