## 第一章 概述

这是第一章的正文。目录应当列出所有标题，并在右侧给出所在页码。为了确保目录跨页，下面填充了足够多的段落。

段落 1：逆向 Typora 的导出流程需要先固定几个事实：渲染引擎版本、打印参数、以及导出前后对 DOM 做的加工。这三者一旦确定，输出就是确定的。

段落 2：Chromium 124 与 153 在默认打印边距的取整上不同，124 取 28.00pt，153 取 27.75pt，于是整页内容会整体平移 0.25pt。这不是排版差异，而是取整差异。

段落 3：中文回退字体的 PDF 表示也变了：153 会为回退字体生成 Type3 字形过程，124 则嵌入真实的字体子集。

段落 4：因此像素级一致必须锁定 124。这一点在 `out/chroma/README.md` 里有完整的测量数据。

段落 5：目录页码的实现依赖 Chromium 为隐藏锚点生成的 `af://` 链接注释，这与 Typora 生成书签时使用的是同一份数据。

段落 6：第一遍打印只为了测量真实分页；第二遍把页码写进目录；如果写入页码改变了分页，就再迭代一次。

### 1.1 小节 A

小节 A 的正文。这里再堆一些文字，让第一章超过一页。

段落 A1：分页测试的目的是让目录中的页码出现多页的情况，从而验证页码提取、锚点匹配、以及目录项与标题的一一对应关系。

段落 A2：如果页码提取失败，目录中的数字会为空，此时应当回退为不带页码的目录，而不是输出错误页码。

段落 A3：如果标题没有对应的锚点（例如标题被包在某种不产生链接的结构里），则跳过该项的页码，而不是写 0。

## 第二章 细节

第二章从一个新的 H1 开始。在 Typora 的导出里，非首个 H1 会带 `data-breakpage`，但消费该属性的 CSS 规则只有在传入 `splitPages` 时才会输出，而 PDF 导出路径从不传，所以它实际上是惰性的。

段落 C1：也就是说，Typora 的 PDF 导出不会在每个一级标题处强制分页。这是我们在 DOM 上保持一致的细节之一。

段落 C2：如果将来要支持"每章新起一页"，需要显式输出那条 `[data-breakpage]` 规则，并把它作为一个可选开关。
